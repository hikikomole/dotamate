## Задача 1. Поднять www.dotamate.ru (~15 минут, риск нулевой)

Сейчас имени `www.dotamate.ru` не существует вообще: DNS-записи нет, браузер у такого
посетителя упрётся в ошибку соединения. Ломать нечего — всё, что мы делаем, только
добавляет.

### Шаг 1.1. Добавить DNS-запись

1. Открыть <https://dash.cloudflare.com/> и выбрать домен **dotamate.ru**.
2. Слева **DNS → Records**, кнопка **Add record**.
3. Заполнить:
   - **Type:** `CNAME`
   - **Name:** `www`
   - **Target:** `dotamate.ru`
   - **Proxy status:** **Proxied** — облачко должно быть **оранжевым**
   - **TTL:** Auto
4. **Save**.

Почему именно так: оранжевое облако обязательно — без него запрос пойдёт мимо
Cloudflare и правило перенаправления из шага 1.2 просто не выполнится. CNAME вместо A
берём, чтобы не править адрес руками, если IP когда-нибудь сменится.

**Проверка:** в списке записей появилась строка `www CNAME dotamate.ru` с оранжевым
облаком.

### Шаг 1.2. Создать правило перенаправления

1. В том же домене слева **Rules → Overview**.
2. **Create rule → Redirect Rule**.
3. Если в списке шаблонов есть готовый **«Redirect from WWW to root»** — взять его,
   он уже заполнен правильно, и шаги 4–6 можно пропустить.
4. **Rule name:** `www → dotamate.ru`
5. **When incoming requests match:** выбрать сопоставление по шаблону (Wildcard
   pattern) и в поле **Request URL** написать:
   ```
   https://www.*
   ```
6. **Then → Type:** `Dynamic`, поле **Target URL**:
   ```
   https://${1}
   ```
   **Status code:** `301`, **Preserve query string:** включить.
7. **Deploy**.

Это ровно тот вариант, что описан в документации Cloudflare для www → apex: звёздочка
захватывает всё после `www.`, `${1}` подставляет захваченное обратно, поэтому
`https://www.dotamate.ru/heroes/pudge/` уедет на `https://dotamate.ru/heroes/pudge/`,
а не на главную. Перенаправления выполняются **раньше** воркера, так что деплой сайта
это никак не затрагивает.

### Шаг 1.3. Проверить

В браузере открыть `http://www.dotamate.ru/guides/` — должно перебросить на
`https://dotamate.ru/guides/`. Если есть терминал:

```
curl -sI https://www.dotamate.ru/guides/
```
Ожидаем `301` и строку `location: https://dotamate.ru/guides/`.

**Откат, если что-то не так:** удалить правило в Rules и запись в DNS. Сайт на
`dotamate.ru` при этом не затрагивается ни на секунду.

**Ссылки:**
[www → apex у Cloudflare](https://developers.cloudflare.com/rules/url-forwarding/examples/redirect-www-to-root/) ·
[как создать Redirect Rule](https://developers.cloudflare.com/rules/url-forwarding/single-redirects/create-dashboard/)

## Задача 2. robots.txt — чинить нечего, но одно решение принять надо

**Что я проверил (25.09.2026).** Живой `robots.txt` — 3259 байт, из них твоих 81.
Cloudflare подставляет свой блок **перед** твоим; твоя часть цела, в конце файла:

```
# END Cloudflare Managed Content

User-agent: *
Allow: /
Disallow: /api/

Sitemap: https://dotamate.ru/sitemap.xml
```

**Главное: Googlebot и YandexBot в блоке отсутствуют.** Поисковой индексации ничего не
мешает. Значит версия «сайта нет в выдаче из-за robots/sitemap» — неверна, причину
надо искать в панелях вебмастера (задача 3).

**Что реально заблокировано:** обучающие и «по запросу пользователя» AI-краулеры —
ClaudeBot, GPTBot, ChatGPT-User, Google-Extended, Google-NotebookLM, MistralAI-User,
Kimi-User, CCBot, Bytespider, Amazonbot, Applebot-Extended, meta-externalagent,
cohere-ai, Diffbot, GoogleOther, а заодно **Baiduspider** (это уже обычный поисковик,
хоть и не наша аудитория). Плюс заголовок `Content-Signal: search=yes, ai-train=no,
use=reference`.

**Решение за тобой, и оно не техническое, а стратегическое:**

- **Оставить как есть** — контент не уходит в обучение чужих моделей. Цена: когда
  человек спрашивает у ChatGPT или Claude «где почитать про броню в доте», твой сайт
  прочитан не будет. Заодно любой внешний AI-аудит сайта будет и дальше возвращать
  мусор — именно на этот блок упёрлась нейросеть, приславшая «sitemap не отдаётся».
- **Разрешить чтение по запросу пользователя, оставив запрет на обучение** — это
  разные группы краулеров, и Cloudflare умеет разделять их в AI Crawl Control.

**Где смотреть и переключать:** Cloudflare → домен dotamate.ru → **Security → Settings**,
фильтр **Bot traffic**, пункт **«Set your preference to block training in robots.txt»**
(это и есть тот самый управляемый robots.txt) и раздел **AI Crawl Control** для
поштучного управления краулерами.

**Ссылки:**
[Managed robots.txt](https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/) ·
[AI Crawl Control](https://developers.cloudflare.com/ai-crawl-control/) ·
[Управление AI-краулерами](https://developers.cloudflare.com/ai-crawl-control/features/manage-ai-crawlers)

Мелочь на потом, не срочно: в файле теперь две группы `User-agent: *` — своя и
Cloudflare. Поисковики такие группы объединяют, `Disallow: /api/` продолжает работать,
ничего не сломано.

## Задача 3. Выяснить настоящую причину отсутствия в выдаче (~20 минут)

Sitemap отдаётся корректно (`HTTP 200`, `application/xml`, 79 КБ), robots не мешает.
Значит ответ лежит в панелях вебмастера, и там его надо просто прочитать.

### Google Search Console — <https://search.google.com/search-console>

1. Убедиться, что домен подтверждён (если нет — добавить ресурс и подтвердить).
2. **Sitemaps**: добавить `sitemap.xml`, дождаться статуса **Success** и посмотреть
   **Discovered URLs** — должно быть около 538.
3. **Indexing → Pages**: сколько страниц «Indexed», сколько «Not indexed» и с какой
   причиной. Именно причина в этой таблице и есть ответ на вопрос «почему сайта нет».
4. **URL Inspection** для `https://dotamate.ru/` — кнопка **Request indexing**.

### Яндекс.Вебмастер — <https://webmaster.yandex.ru>

1. **Индексирование → Файлы Sitemap**: добавить `https://dotamate.ru/sitemap.xml`.
2. **Индексирование → Страницы в поиске**: сколько загружено и сколько в поиске.
3. **Диагностика → Диагностика сайта**: там Яндекс прямо пишет найденные проблемы.

Для русскоязычной аудитории Яндекс важнее Google, поэтому начинать с него.

**Чего ожидать честно:** молодому сайту с 538 страницами на полную индексацию нужны
недели, а оператор `site:` показывает не всё и не сразу. Пришли мне скриншоты или цифры
из этих двух панелей — по ним я скажу, есть ли реальная проблема или надо просто ждать.

## Чего не делаем (и почему)

| Пункт присланного промпта | Почему нет |
| --- | --- |
| Рефакторинг `server.js`, миграции Postgres, Redis, WebSocket-лимиты, CloudPayments, Docker, Caddy | Сайт обслуживает только Cloudflare Worker со статикой. Этот код сейчас не отвечает ни на один запрос посетителя |
| Переезд в `src/backend` / `src/frontend` / `dist` | Переписывает сборку, которая даёт 537 страниц и ноль битых ссылок |
| Минификация, хеширование ассетов, ES-модули | То же самое: большой риск ради внутренней аккуратности |
| Смена `D2H_CACHE_VERSION`, JWT-issuer и прочих namespace | Это ключи в localStorage у живых посетителей: смена разом обнуляет их кэш |
| Чистка git history | Ничего не возвращает: утёкший токен спасает только отзыв |
| Любые изменения URL | Ломает SEO. Если URL всё же меняется — только с 301 |
