## Проверка живого сайта: 25.09.2026, 01:11 UTC

Проверено curl'ом с машины владельца по подключённой папке проекта.

| Утверждение из отчёта нейросетей | Факт |
| --- | --- |
| `sitemap.xml` не отдаётся, ошибка сервера | **Неверно.** `HTTP/2 200`, `content-type: application/xml`, `cf-cache-status: HIT`, 79 134 байта. Файл есть и в `deploy/`, и на сайте |
| `www.dotamate.ru` отвечает таймаутом | **Проблема есть, причина другая:** DNS-записи `www` не существует (`getent hosts` → пусто, TLS рвётся на установке соединения). Это не таймаут сервера, а отсутствие имени |
| Главная | `HTTP/2 200`, заголовки безопасности на месте: CSP, `x-content-type-options`, `referrer-policy`, `permissions-policy` |

**Почему нейросети увидели «ошибку сервера».** Живой `robots.txt` отдаёт
**3259 байт**, тогда как в репозитории лежит файл на **81 байт** (`User-agent: *` /
`Allow: /` / `Disallow: /api/` / строка Sitemap). То есть Cloudflare подменяет или
дополняет robots.txt — почти наверняка включён управляемый robots с блокировкой
AI-краулеров. Мой собственный загрузчик получил ровно это: отказ по robots на
*любой* URL сайта, включая сам robots.txt. Внешний аудитор-нейросеть, упершись в тот
же блок, принял его за битый sitemap.

**Вывод: из двух «подтверждённых проблем» подтвердилась одна — www.**
Это хорошая иллюстрация правила: чужой отчёт проверяется, а не выполняется.

## Где присланный аудит расходится с реальностью

**Допущение промпта:** в проде две архитектуры — Worker и Node/Express + PostgreSQL +
Redis + MediaMTX + TURN + CloudPayments за Caddy, их надо свести.

**Факт:** dotamate.ru обслуживает только воркер со статикой. Значит пункты 13–24,
61–67, 87–89 (модуляризация `server.js`, миграции, graceful shutdown, WebSocket
rate limit, CloudPayments, health-эндпоинты, CORS) — работа над кодом, который сейчас
не отвечает ни на один запрос посетителя. Ноль пользы, ненулевой риск. **Не делаем.**

**Цена «красивой» сборки.** Пункты 26, 31–35, 50, 99 (asset hashing, минификация,
ES-модули, `dist/`, переезд в `src/frontend/...`) переписывают ровно тот код, который
даёт 537 страниц и ноль битых ссылок. Это главный способ потерять SEO ради внутренней
аккуратности. **Не делаем.**

**Порядок работы с секретами.** Чистка git history ничего не возвращает: попавший в
репозиторий токен уже скомпрометирован. Сначала отзыв и выпуск новых, история — потом
и только при доказанной утечке.

## Что делаем (риск близок к нулю)

### 1. www.dotamate.ru — единственная подтверждённая проблема

Сейчас имени не существует, ломать нечего.

1. Cloudflare → DNS → Add record: `CNAME`, имя `www`, target `dotamate.ru`,
   Proxied (оранжевое облако).
2. Cloudflare → Rules → Redirect Rules → Create:
   условие `hostname eq "www.dotamate.ru"`,
   действие Dynamic 301 → `concat("https://dotamate.ru", http.request.uri.path)`,
   Preserve query string — включить.
3. Проверка: `curl -sI https://www.dotamate.ru/heroes/` → `301` и
   `location: https://dotamate.ru/heroes/`.

Риск: нулевой, деплой воркера не затрагивается, откат — удаление записи.

### 2. Разобраться с robots.txt (только посмотреть, менять по результату)

Живой файл втрое с лишним больше репозиторного. Надо открыть Cloudflare →
настройки бота/AI-краулеров и увидеть, что именно подмешивается. Два исхода:

- если блокируются только AI-краулеры (GPTBot, ClaudeBot и подобные) — это осознанный
  выбор, трогать не надо, но надо знать: любой внешний AI-аудит сайта будет и дальше
  возвращать мусор;
- если под блок попал Googlebot или YandexBot — это реальная беда для индексации,
  и вот её чинить надо немедленно.

Пока не увидим содержимое — никаких правок.

### 3. Переотправить sitemap в Search Console и Яндекс.Вебмастер

Карта отдаётся корректно, но раз сайт не находится по `site:dotamate.ru`, дело не в
файле. Переотправка карты + проверка отчёта об индексации покажет настоящую причину
(возраст домена, robots, ручные санкции — разные истории).

## Что важнее любой архитектуры: фактические ошибки на страницах

Их видит посетитель, и они бьют по доверию сильнее монолитного `server.js`.

1. **Фасеты.** Патч 7.41 убрал их из игры целиком, а на страницах героев остались
   иконки и блоки. Порядок: `grep -rn "facet\|фасет" js/ data/ build-hero-pages.js`,
   решить — убрать или пометить «удалено в 7.41», пересобрать, прогнать
   `tools/check-links.js`.
2. **Расхождение в каталоге предметов**: «253 в базе» против «загружено 345».
   Одна из цифр врёт; привести к одному источнику.
3. **Русские названия талантов** уже лежат в `data/talents-ru.json`, включаются одной
   строкой в `build-hero-pages.js` (`talentNames:null` → `talentNames`).

Риск средний и управляемый: правки идут через обычный цикл сборки, результат
проверяется `check-links.js` и сравнением HTML до/после.

## Что не делаем

- Рефакторинг `server.js`, миграции Postgres, Redis, WebSocket-лимиты, CloudPayments,
  Docker, Caddy — пока эта подсистема не понадобится в проде.
- Переезд в структуру `src/backend`/`src/frontend`/`dist`.
- Минификация, хеширование ассетов, переход на ES-модули.
- Переименование `D2H_CACHE_VERSION`, JWT-issuer и прочих namespace: это ключи в
  localStorage у живых посетителей, смена разом обнуляет их кэш.
- Массовое удаление «мёртвого кода» по результатам grep.
- Любые изменения URL. Если URL всё же меняется — только с 301.
- Чистка git history.

## Правила безопасности работ

1. Одна правка — один деплой; перед деплоем записать текущую версию воркера
   (`npx wrangler deployments list`), откат — `npx wrangler rollback <id>`.
2. После деплоя: `node tools/check-links.js` + `curl -sI` по главной, странице героя,
   странице предмета, гайду и sitemap.
3. `deploy/` руками не редактируется — только `build-*.js` и `tools/sync-deploy.js`.
4. Перед удалением файла — `grep -rn` по имени во всём репозитории, включая HTML,
   сборщики и `wrangler.jsonc`.
