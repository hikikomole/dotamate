# D2PT features implementation plan

> Planning only, 2026-10-26. Implement stages in separate Codex runs using `superpowers:executing-plans`. This document does not authorize deployment, collection requests, or changes to production. No implementation was performed.

**Goal:** add useful Dota statistics without using OpenDota/Stratz as public statistical sources.
**Architecture:** static HTML/CSS and vanilla JS; Node builders produce small versioned aggregates. Steam match records and Valve replays supply measurements; Valve datafeed supplies patch/reference data. Keep cohorts separate and reuse existing tables, cards, role icons and CSS tokens.
**Tech stack:** existing CommonJS Node, browser JS, PHP live API; no new dependencies.
**Spec:** the feature request in this session; source policy in `docs/architecture/data-independence.md`.

## Shared contracts and methods

All new aggregate JSON uses `{schemaVersion:1, builtAt, status, meta, ...}`. `status` is `ok|insufficient|unavailable`; `meta` includes structured `source`, `cohort`, `patch`, `patchFrom`, `from`, `to`, `matches`, `players` where applicable, `methodVersion`, exclusions and coverage. Timestamps are UTC ISO, raw match timestamps seconds, durations/timings seconds, public percentages 0–100, deltas percentage points. Unknown is null, never zero. Keep raw integer wins/appearances and round only display fields.

New builders accept `--input-dir`, `--out-dir`, `--fixture`, and when needed `--archive-dir`; fixture mode is offline and never falls back to real data. Resolve all output paths under the requested directory. Existing hardcoded-output builders must gain explicit isolation before test commands invoke them. Atomic write plus validation; preserve last good output on failure, and show its actual date. Valid empty cohort produces an explicit insufficient result rather than silently carrying a different cohort forward. A build timestamp must not refresh source-data freshness.

Five-role ranking, feature #1:

```
n = distinct hero-player appearances in eligible matches at position p
w = wins among those appearances; z = 1.96; q = w/n
L = (q + z*z/(2*n) - z*sqrt(q*(1-q)/n + z*z/(4*n*n))) / (1+z*z/n)
rating = round(100*L, 2)
```

This is a conservative winrate score, NOT a probability of winning the next game and NOT a percentile. Require n>=100 for rating/tier; 30–99 display count/raw WR with “small sample”, rating/tier null; below 30 hide WR, retain counts in coverage. Sort using unrounded L, then n descending, then hero ID ascending. Within each position's eligible heroes assign S to first ceil(20%*K), A to next through ceil(50%*K), B to the rest; if K<5 leave tiers null and explain insufficient coverage. Do not change the legacy S/A/B/C/D scheme implicitly. Role pick share = n / number of labeled eligible player slots at that position, with denominator explicit. Role estimates and Wilson intervals do not account for systematic classification error or correlated pro teams.

Role gate: manually audit at least 100 teams across different days/lineups using only replay evidence; record confusion counts and ambiguous labels. Require >=85% agreement for EACH role on at least 50 audited player labels per role and >=90% labeling coverage for the published replay cohort. This is a proposed release gate, not claimed existing accuracy. Exclude ambiguous assignments; if it fails, ship an insufficient-data state, never split the combined Steam support bucket. Do not increase collector load automatically.

Shared frontend states: static heading/method/source remain visible; async tables get loading text with aria-live, retry on network/JSON errors, valid-empty and low-sample messages. Stale threshold 36h uses input data date; static pages also render dates without JS. No fallback to excluded sources. Tables scroll inside their wrapper at 390px; filters stack at <=900px; keyboard controls and focus, light/dark themes, no color-only tier/delta meaning. Feature-specific cases follow below.

### 4. Radiant/Dire — sides/duration feasible, lanes conditional, L

Steam supports outcome by duration and hero side. Add raw per-side hero appearances/wins; hero delta = Radiant hero WR minus Dire hero WR, not difference of appearance counts. Duration buckets match current `[900,1500),[1500,2100),[2100,2700),[2700,infinity)`; each match contributes exactly one Radiant outcome. Minimum 300 matches per duration bucket and 100 hero appearances EACH side for displayed delta/interval; show counts otherwise. Describe short-match anomalies documented 17 October; no causal interpretation or blanket “advantage”.

Files: create `tools/build-side-stats.js`, extend `js/stats.js` matches view, `page-sections.html`, `css/stats.css`; reuse shared cohort reader. Output `data/side-stats.json={meta,duration:[{key,n,radiantWins,radiantWr}],heroes:[{id,radiant:{n,w,wr},dire:{n,w,wr},delta}],lanes}`. API static file; existing stats base.radiantWr retained. Lane data requires replay coordinates and matched 10-minute economy, not final Steam stats or Stratz `m.lanes`. Separate physical top/mid/bot from side-relative safe/offlane. Proposed lane outcome: sum net worth at 10:00 for assigned same-lane players; Radiant win if R/D>1.05, Dire win if R/D<1/1.05, otherwise tie; missing positive comparable samples => unknown. Publish this as a site heuristic, not Stratz outcome. Counts once per physical lane per match; hero lane rows have their own denominator. Minimum 100 comparable lane observations. States: sides can work while lanes say unavailable. Docs: both, including method and mapping. Risks: missing snapshots, rotations, duration conditioning; L.
