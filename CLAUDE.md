## Что это за проект

Неофициальный сайт-помощник по Dota 2: герои, предметы, статистика, гайды, инструменты (калькулятор MMR,
рандом героя и т.п.) + встроенная стриминговая платформа (каналы, лайв через WebRTC/RTMP/HLS, чат, подписки,
донаты через CloudPayments). Фронтенд — статические HTML-страницы + vanilla JS, без фреймворка.

**Бизнес-цель:** сайт должен зарабатывать на контенте — реклама и партнёрские ссылки (гейминг-товары,
хостинг рефералки, донаты/CloudPayments уже реализованы). Это значит: SEO, скорость загрузки и удобство
чтения гайдов важны не меньше, чем новый функционал.

## Стек

- **Backend:** Node.js, без фреймворка — чистый `http` модуль (`server.js`, ~40к строк кода в одном файле).
  PostgreSQL (`pg`), Redis (`redis`), WebSocket (`ws`), JWT (`jsonwebtoken`), bcrypt (`bcryptjs`).
- **Frontend:** статический HTML + vanilla JS (`js/app.js`, `js/stream.js`, `js/studio.js`, `js/v43-*.js`) + CSS
  (`css/style.css` — большой основной файл, `css/stream.css`, `css/studio.css`, `css/v43-platform.css`).
- **Стриминг:** MediaMTX (WebRTC/WHIP/RTMP/HLS), Coturn (TURN для WebRTC ICE).
- **Инфраструктура:** Docker Compose (`docker-compose.yml`), Caddy как HTTPS reverse proxy (`Caddyfile`).
- **Данные о героях/предметах:** проксируются с dota2.com / OpenDota / dotaconstants (см. `js/app.js`,
  `dotaProxy` в `server.js`).

## Карта данных — какой файл за что отвечает (prod vs preview)

**Важно с 21.09.2026: к предметам всё написанное ниже больше не относится.**
Список предметов, описания и картинки теперь целиком локальные — см. раздел
«Предметы: локальная русская база». Прокси `/api/dota/items` и `/api/dota/item/:id`
в `server.js`, `preview-server.js` и `deploy/worker.js` оставлены (их ещё
использует `tools/fetch-hero-guide-data.js` для способностей героев), но сайт
в них не ходит. Ниже — про героев и про то, как устроены прокси.

Это осознанно два РАЗНЫХ по возможностям сервера, и они расходятся по-настоящему — вот что именно
куда ходит, чтобы это не пришлось каждый раз заново разбирать:

- **`preview-server.js`** (локальный запуск, `Open Dota 2 Helper.cmd`) — самый полный источник:
  - Список героев/предметов: опрашивает по очереди Valve datafeed → OpenDota → dotaconstants (GitHub),
    берёт первый успешный как основу и досливает поля из остальных (`refreshHeroes`/`refreshItems`,
    `mergeHeroStats`/`mergeItems`). Кэширует результат на диск (`.d2h-data-cache-v43/`).
  - Детали предмета (`/api/dota/item/:id`) и способности героя (`/api/dota/hero/:name/abilities`) —
    тянет с Valve datafeed / OpenDota `constants/hero_abilities`+`constants/abilities`, переводит через
    `translateToRu()` (DeepL, кэш на диске).
- **`server.js`** (прод, `dotaProxy` для `/api/dota/heroes` и `/api/dota/items`) — использует Redis-кэш
  вместо дискового (не диск, как в preview), и не полностью 1-в-1 с preview:
  - `/api/dota/heroes` — опрашивает **только OpenDota** (без Valve/dotaconstants), но этого достаточно:
    OpenDota `heroStats` уже содержит всё нужное поле `name`, багов не было.
  - `/api/dota/items`, `/api/dota/item/:id`, `/api/dota/hero/:id/items`, `/api/dota/hero/:name/abilities` —
    все **перенесены/дополнены** до того же уровня, что и `preview-server.js` (см. «Технические долги»
    ниже), включая то же слияние Valve → OpenDota → dotaconstants для списка предметов.
- **`js/app.js`** (клиент) — своя копия `normalizeHeroes`/`normalizeItems`, логически зеркалит то, что
  делает `preview-server.js` при слиянии (в т.ч. правило фильтрации рецептов). Это дублирование кода
  специально: клиент должен уметь сам нормализовать данные независимо от того, какой сервер ответил.
- **Русский текст описаний способностей/предметов** — в обоих серверах одинаковый набор функций
  (`parseVdfTokens`/`buildAttribMap`/`fillPlaceholders`/`hasUnresolvedPlaceholder`/`getOfficialRuMap`/
  `resolveRuText`, имена намеренно совпадают) реализует цепочку источников: официальный русский текст
  Valve (см. «Официальный RU-текст» ниже) → DeepL → английский оригинал. Каждое описание получает поле
  `source` (`'official-ru' | 'deepl' | 'en'`), которое `js/app.js` показывает пользователю через
  `sourceLabel()`. Если меняешь эту логику в одном файле — обнови и второй.

**Правило:** если правишь `server.js` или `preview-server.js` — проверь, не разошлась ли логика с другим
файлом (особенно `normalizeItems`/`normalizeHeroes`/фильтры категорий). Расхождение незаметно копится и
именно так возникла часть багов, описанных ниже. Если меняешь фильтрацию/нормализацию данных в одном
файле — загляни в `js/app.js`, `preview-server.js` и `server.js` разом и обнови все три, если применимо.

## Структура страниц — сайт разделён на разделы (21.09.2026)

Раньше весь сайт был одной страницей: `index.html` содержал шесть разделов
подряд, переходы шли якорями (`#heroes`, `#items`). Для поиска это одна
страница с одним `<title>`, и по запросу «предметы Dota 2» показать было
нечего, кроме главной. Теперь у каждого раздела свой адрес:

```
/          главная — баннер, быстрый пик, карточки разделов, подборка героев
/heroes/   каталог героев
/items/    каталог предметов
/stats/    таблица статистики
/guides/   гайды
/game/     мини-игра Hook & Hit
```

**Страницы не правятся руками.** Их собирает `node build-pages.js` из двух
источников:

- `page-shell.html` — общий каркас: голова с плейсхолдерами `{{TITLE}}`,
  `{{DESC}}`, `{{CANONICAL}}`, `{{NAV}}`, `{{BREADCRUMBS}}`, `{{CONTENT}}`,
  `{{PAGE_SCRIPTS}}`, шапка, подвал, модалка, общие скрипты.
- `page-sections.html` — разметка самих секций, по одной на раздел, каждая
  со своим `id`. Сборщик режет файл по началу строки `<section`.

Конфигурация страниц (адрес, заголовок, описание, какие секции включить) —
массив `PAGES` внутри `build-pages.js`. Там же `HOME_CARDS` — карточки-входы
на главной. Скрипт пишет результат и в корень проекта (для preview-server), и
в `deploy/`, и обновляет `page-urls.json`, который подхватывает
`build-sitemap.js`.

Правишь разметку раздела — правь `page-sections.html` и пересобирай. Правишь
шапку, подвал или мета-теги — правь `page-shell.html`. Менять `index.html`
или `heroes/index.html` напрямую бесполезно: следующая сборка затрёт.

**Пути к ресурсам абсолютные** (`/css/style.css`, `/js/app.js`): страницы
лежат в подпапках, и относительный путь с `/heroes/` указывал бы на
`/heroes/css/style.css`. Открывать страницы двойным кликом как файлы больше
нельзя — только через `Open Dota 2 Helper.cmd`.

**`js/game.js` грузится только на `/game/`** (30 КБ на остальных страницах ни
к чему) — через `scripts` в конфиге страницы.

### Что это потребовало от app.js

До разделения все секции жили на одной странице, и записи в DOM шли без
проверок. Теперь на `/items/` нет сетки героев, и запись
`document.getElementById('heroesGrid').innerHTML = …` роняла бы загрузку
целиком: приложение уходило в аварийный `catch` и не показывало ничего.

В начале `js/app.js` добавлены `d2hSetText(id,v)` и `d2hSetHtml(id,v)` —
пишут только если элемент есть. Через них проходят `updateHeroUI`,
`renderHeroes`, `renderGuides`, `updateItemCounters`. `renderItems`,
`renderStats`, `renderFeaturedHeroes`, `renderHeroSpotlight` были защищены
изначально.

**Правило:** добавляешь в `app.js` запись в DOM — делай её через эти
помощники либо с проверкой. Иначе функция сломается на той странице, где
нужного элемента нет, и утащит за собой всю загрузку данных.

## Оформление в духе dota2.com (21.09.2026)

Тёмная тема живёт в отдельном файле `css/theme-dark.css` и действует только
внутри `body.d2-dark`. Раздел получает её через `styles` и `bodyClass` в
`build-pages.js`, статические страницы героев и предметов
(`build-hero-pages.js`, `build-item-pages.js`) ставят класс сами. Сейчас она
включена везде: все шесть разделов, 127 страниц героев, 263 страницы
предметов. Светлая тема из `style.css` никуда не делась — она под низом, и
именно поэтому её приходится перебивать (см. ниже).

**Светлые правила перебиваются переменными, а не перечислением блоков.**
`css/style.css` — плотный файл, где поверх исходной тёмной вёрстки лежит
светлая тема «companion» с `!important` почти в каждой строке. Внутри
`body.d2-dark` переопределены сами переменные (`--comp-bg`, `--comp-surface`,
`--comp-text`, `--comp-border`, `--comp-accent` и т.д.) — этого хватает на
большинство блоков. Точечные правила нужны только там, где в style.css
зашит литерал (`background:#fff!important` у полей ввода, подвала и модалки,
белая кнопка меню на телефоне). Любое новое правило темы тоже требует
`!important`, иначе его перебьёт светлая тема.

### Фоновое видео на главной

Ролик берётся у Valve:
`https://cdn.steamstatic.com/apps/dota2/videos/dota_react/homepage/dota_montage_02.mp4`
(~21 МБ) и `…/dota_montage_webm.webm` (~24 МБ) как запасной — Chromium без
проприетарных кодеков играет именно его. Домен уже прописан в `media-src` в
`_headers`; для нового видеохоста CSP придётся дополнять.

Чтобы 21 МБ не грузились у каждого:

- у `<video>` стоит `preload="none"`, до запуска виден `poster`
  (`assets/home-bg-poster.jpg`, 62 КБ) — это первый кадр того же ролика,
  вырезанный ffmpeg, поэтому подмены не видно;
- `js/home-bg.js` (подключён только на главной через `scripts`) запускает
  видео, когда первый экран попал в зону видимости, и не запускает вовсе при
  `navigator.connection.saveData`, `effectiveType` 2g и
  `prefers-reduced-motion`;
- кнопка паузы `#homeBgToggle` запоминает выбор в `localStorage` (`d2hHomeBg`).

Если ролик заменяется — поменять и постер: несовпадение кадра даёт заметный
рывок в момент старта.

### Подборка «Быстрый выбор героя»

Две правки, которые легко откатить назад по невнимательности:

- подпись карточки (`.featured-hero-card > div`) нигде не позиционировалась,
  вставала под картинкой и срезалась `overflow:hidden` — на экране оставалась
  голая картинка. Теперь подпись лежит поверх низа карточки, как и
  предполагала градиентная подложка `:after`;
- сортировка идёт по `wrScore()` в `js/app.js` — нижней границе
  доверительного интервала Уилсона (95%) для доли побед, а не по сырому
  winrate. Раньше в подборку попадали герои с одним-двумя про-пиками и
  «100.0%». Показывается при этом настоящий процент и число пиков рядом —
  оценка влияет только на порядок.

### Предметы: локальная русская база (21.09.2026)

**Сайт больше никуда не ходит за предметами.** Ни за описанием, ни за ценой,
ни за картинкой. Всё лежит в репозитории:

```
data/items-ru.json     345 предметов: русское описание, история, примечания,
                       бонусы, цена, компоненты, во что входит (≈280 КБ)
data/item-heroes.json  предмет -> герои, которые его покупают (≈88 КБ)
data/hero-items.json   герой -> покупки по фазам игры (≈46 КБ)
assets/items/*.png     263 иконки предметов, ~3,2 МБ
```

Каталог `/items/`, модалка предмета, страницы `/item/<slug>/`, блок покупок в
карточке героя и «Самые покупаемые предметы» на `/stats/` читают эти четыре
источника и ничего больше. Раньше каждый из этих блоков дергал Valve datafeed
или OpenDota прямо из браузера: на статическом проде половина запросов
упиралась в CORS, описания оставались английскими, а блок аналитики показывал
«Выборка: 0 предметов».

**Откуда данные.** Официальный **русский** datafeed Valve:
`https://www.dota2.com/datafeed/itemdata?language=russian&item_id=N`. Он отдаёт
сразу и текст (`desc_loc`, `lore_loc`, `notes_loc`), и числа (`special_values`),
которыми заполняются `%плейсхолдеры%` в тексте. Это лучше, чем прежняя связка
«английский OpenDota + отдельный файл локализации»: текст и числа приходят из
одного места и не расходятся. Файл `abilities_russian.txt` всё ещё нужен, но
только ради словаря переменных (`$str` -> «к силе») для подписей бонусов.

**Цепочка сборки** (первые три шага ходят в сеть, четвёртый — нет):

```
python3 tools/fetch-item-sources.py     # OpenDota constants/items + локализация
python3 tools/fetch-valve-items-ru.py   # русский datafeed по каждому предмету (~4 мин)
python3 tools/fetch-item-icons.py       # иконки в assets/items/
python3 tools/build-items-ru.py         # data/items-ru.json
python3 tools/build-item-heroes.py      # data/item-heroes.json + data/hero-items.json
node build-item-pages.js                # 262 страницы предметов
node build-sitemap.js
node tools/sync-deploy.js               # копирует статику в deploy/
```

`fetch-valve-items-ru.py` дозагружает недостающее при повторном запуске, поэтому
обрыв на середине не страшен. Три иконки (`phylactery`, `angels_demise`,
`disperser`) у Valve анимированные и весят по 2 МБ — они пересохранены первым
кадром (Pillow), иначе одни только они дали бы +6 МБ в деплой.

разные байты — это оно, искать нечего.

**Что изменилось в цифрах.** Каталог показывает 345 предметов вместо 346:
`diffusal_blade_2` убран, потому что его нет в официальном datafeed Valve —
вторая ступень Diffusal Blade из игры удалена, а OpenDota её всё ещё хранит.

### Всё своё: картинки и списки больше не тянутся со стороны (23.09.2026)

К предметам добавились герои и способности. Что теперь лежит в репозитории:

**Что осталось внешним и почему.** На CDN Valve остались только видеоролики —

работает на снимке, просто про-цифры будут от даты сборки. Список героев больше
не гоняется наперегонки из трёх источников: Valve datafeed из браузера не
читается вовсе (нет CORS), а зеркало на raw.githubusercontent.com было лишним

таланты (`bristleback_prickly`, `axe_one_man_army` и подобные), у них на CDN

заглушка; обработчик ошибок в `js/app.js` теперь следит только за `/assets/`,

### Ещё одна выдуманная цифра, которой больше нет

В модалке героя у каждой покупки печаталось «0.0% побед». OpenDota в
`itemPopularity` отдаёт только счётчик покупок, поля `wins` там нет вовсе, а
проверка стояла `wins >= 0` — то есть ноль показывался как измеренный
результат. Теперь процент выводится только при `wins > 0`.

## Стиль кода — ВАЖНО

Существующий код (особенно `server.js`, `js/app.js`) написан очень компактно: длинные однострочные
функции, минимум пробелов, без промежуточных переменных ради краткости. Это осознанный стиль автора.

**Правило:** при правке существующих файлов — следуй тому же компактному стилю, чтобы не превращать
файл в смесь двух почерков. Для НОВЫХ отдельных файлов можно писать более читаемо, если не просят иначе.
Не переписывай/не рефактори большие куски «заодно» без явной просьбы — в таком плотном коде это легко
что-то незаметно сломает.

## Безопасность — нельзя нарушать

- `.env` и всё содержимое `secrets/` никогда не коммитятся и не выводятся в чат целиком.
- `JWT_SECRET`, `TURN_SECRET`, ключи CloudPayments — только через переменные окружения/секреты,
  никогда не хардкодить и не передавать в браузер.
- Stream key канала — секрет владельца канала, не логировать и не вставлять в открытые страницы/доки.
- CSP настроен в `securityHeaders()` в `server.js` (`server.js`, строка со `Content-Security-Policy`).
  **Любой новый внешний скрипт (рекламная сеть, аналитика, виджет) требует добавления его домена в CSP**,
  иначе он молча не заработает в браузере — не забывай про это при добавлении рекламы/аналитики.
- CSRF-токен и Origin-проверка уже реализованы для всех небезопасных методов — не отключать ради
  «упрощения» отладки.

## Монетизация и рост (контент + реклама/партнёрки)

Когда просят добавить рекламу, партнёрские блоки, аналитику или новый контент (гайды, лендинги):

- SEO: у каждой значимой страницы должны быть уникальные `<title>` и `<meta name="description">`
  (уже частично сделано на index.html — держи такой же паттерн для новых страниц/гайдов).
- Скорость: реклама не должна блокировать рендер страницы — грузить асинхронно/отложенно (`async`/`defer`,
  lazy-load для баннеров ниже первого экрана).
- Партнёрские ссылки помечать `rel="sponsored"` (важно для Google) и по возможности явно подписывать
  «партнёрская ссылка» рядом — это и требование площадок, и вопрос доверия аудитории.
- Не размещать интерстишлы/попапы, перекрывающие контент на мобильных — это бьёт и по SEO, и по удержанию.
- Не забывать про CSP (см. раздел «Безопасность») при подключении рекламных/аналитических скриптов.
- Донаты через CloudPayments уже есть — это тоже канал монетизации, отдельный от рекламы.

История правок сессий 1–5 (16.09.2026) свёрнута до итогов. Ниже — только то, что
действует сейчас: инварианты, которые нельзя сломать, и незакрытые хвосты.

### Инварианты — сломать легко, заметить трудно

- **Рецепты не фильтровать.** Рецепт — реальный покупаемый предмет со своей ценой,
  и в каталоге есть категория «Рецепты». Сейчас каталог показывает 345 предметов,
  из них 83 рецепта; если рецепты пропали — вернулся старый фильтр `item_recipe_*`.
  Отбор идёт один раз, при сборке `data/items-ru.json`, а не в браузере.
- **`dotaProxy` для `/api/dota/items` обязан сливать Valve → OpenDota → dotaconstants.**
  Объекты OpenDota `constants/items` не содержат поля `name` (оно в ключе объекта), а
  клиентский `normalizeItems` требует `raw.id && raw.name` — без слияния список предметов
  на проде окажется пустым. Для `/api/dota/heroes` этого не нужно: у `heroStats` поле
  `name` есть.
- **`getItemDetail`/`getItem` перезаписывают и `desc_loc`, и `description`** результатом
  `resolveRuText` (или пустой строкой). Иначе старое английское значение из Valve datafeed
  просачивается на экран в обход перевода через `||` в `js/app.js`.
- **`resolveRuText(internalKey, isItem, attribArr)`** отдаёт либо официальный RU-текст, либо
  `{text:'', source:'none'}`. Параметра `fallbackEn` нет, DeepL удалён полностью. Пустую
  строку фронтенд подхватывает готовыми заглушками — отдельной обработки не требует.

### Источник русских текстов

Официальная локализация Valve из репозитория `dotabuff/d2vpkr`
(`dota/resource/localization/abilities_russian.txt`) — извлекается из файлов игры, обновляется

### Правило работы — делегирование по умолчанию (23.09.2026)

Этот блок продублирован в инструкциях проекта на claude.ai, чтобы правило
действовало и в чатах, и в сессиях Claude Code. Если правите здесь — поправьте
и там, иначе разойдутся.

**Делегирование — режим по умолчанию, разрешения на него не спрашивают.**

Перед объёмной работой решить: механика или решение. Механику отдать в
`tools/llm.py`, решение оставить себе. Если одно и то же повторяется больше
десяти раз по шаблону — это механика, даже если отдельные куски кажутся
творческими.

- **Отдавать:** массовые тексты и SEO-описания, разбор чужого большого файла
  (карта функций вместо чтения 25k токенов), классификацию, конвертацию
  форматов, извлечение JSON, массовые проверки «да/нет», черновики.
- **Не отдавать:** архитектуру, правки `server.js` и `deploy/worker.js`, всё
  вокруг безопасности и денег (JWT, CloudPayments, CSP), финальную проверку —
  проверяет Claude, а не вторая модель.

**Почему это записано так жёстко.** Связка была настроена 18.09.2026, правила
лежали в этом файле — и всё равно 97 описаний предметов для
`tools/item-text-own.json` были написаны вручную, своими лимитами. Правило без
отчётности не работает, поэтому: **если делегировать было можно, но сделано
самому — назвать причину вслух.** Отговорка «так быстрее» должна стоить
объяснения, иначе она побеждает всегда.

**Отчётность:** говорить, что именно и какой модели отдано. Текст внешней
модели, попавший на сайт без переписывания, подписывается так же, как
собственные тексты («текст сайта»).

```
python3 tools/llm.py "перепиши короче"                       # groq по умолчанию
python3 tools/llm.py -p gemini -f js/app.js "карта функций"   # большой файл
cat index.html | python3 tools/llm.py "найди незакрытые теги"
python3 tools/llm.py -p groq --list                           # живые модели по ключу
python3 tools/llm.py --check                                  # кто отвечает прямо сейчас
```

Флаги: `-s` системная инструкция, `-t` температура, `-f` приложить файл (можно
несколько), `-m` конкретная модель, `--no-cross` не перекидывать на другого
провайдера при отказе.

**`--check` прогонять перед каждой объёмной задачей.** Бесплатные тарифы
меняются молча: модель исчезает из каталога, ключ упирается в суточный лимит,
провайдер закрывает регистрацию. Минута на проверку дешевле, чем обрыв на
середине трёхсот запросов.

### Кому что отдавать

- **Ollama** (`-p ollama`) — локальные модели на самой машине, `127.0.0.1:11434`.

  качество зависит от того, какая модель скачана (`ollama list` покажет). Для
  массовой механики на сотни запросов это главный путь: облачные лимиты тратить
  на такое незачем. Имя модели в коде не зашито — при пустом `-m` берётся первая
  установленная.
- **Gemini** (`-p gemini`) — где нужен смысл и разнообразие: тексты, SEO-описания,

### Что нельзя отправлять внешним моделям

Содержимое `.env`, `secrets/`, `JWT_SECRET`, `TURN_SECRET`, ключи CloudPayments,

проверить, что в нём нет строки вида `ghp_*`, `github_pat_*` или URL с `//<токен>@`.
Токен, который пользователь прислал в чат, считать одноразовым: после использования
попросить его отозвать.

## Как читать и править файлы этого проекта (экономия лимитов)

Файлы здесь крупные: `css/style.css` ~25k токенов, `js/app.js` ~21k, `server.js` ~15k;
весь код целиком — ~117k токенов. Поэтому:

- **Искать — `grep`/`rg`**, а не «прочитать файл целиком». Нужную функцию или правило
  находить по имени с парой строк контекста (`grep -n -C3`), а не вычитывая файл.
- **Править — `sed -i`** или короткий скрипт на python, читающий файл сам. Никогда не
  пересобирать файл, перепечатывая его содержимое из вывода предыдущей команды: вывод
  бывает обрезан, и так теряются куски (в плотном стиле этого проекта — незаметно).
- **Читать целиком** только то, что собираешься переписать целиком, либо небольшие файлы
  (`js/v43-features.js`, `js/reliable-data.js` и подобные).
- **Разобраться в большом чужом файле** — отдать его Gemini (`tools/llm.py -p gemini -f ...`),
  см. раздел «Делегирование рутины». Результат — карта функций вместо самого файла.

Оговорка: когда правка завязана на окружающий контекст, прочитать нужный кусок файла —
нормально. Экономия не в том, чтобы не читать вовсе, а в том, чтобы не читать 25k токенов
ради одной строки.

Где идёт работа — зависит от сессии. Если у Claude есть `device_bash`, правки делаются
прямо в папке проекта на машине пользователя. Если его нет (сессия в облачной песочнице),
Claude работает в своей копии репозитория и переносит файлы обратно через
`device_commit_files` — по 50 файлов за вызов. Тогда выгоднее переносить **исходники**
(`js/`, `css/`, `tools/`, `data/`, `page-sections.html`, сборщики), а сгенерированные
страницы и копии в `deploy/` пересобирать уже на машине пользователя командами сборки.
В облачной песочнице сеть из Node и из python3 работает, так что сборщики данных можно
гонять там.

## Мост к командной строке — `Claude outputs\claude-shell.cmd` (23.09.2026)

Когда `device_bash` в сессии нет, Claude раньше писал одноразовый `.cmd` и просил
пользователя щёлкнуть по нему — на каждую команду отдельный файл, отдельная просьба,
отдельное ожидание. Теперь есть постоянный канал.

**Как работает.** Пользователь запускает `claude-shell.cmd` один раз и оставляет окно
открытым. Скрипт раз в три секунды смотрит папку `Claude outputs\shell\in\`: всё, что
там появилось с расширением `.cmd`, он выполняет **в корне проекта**, кладёт вывод и
код возврата в `Claude outputs\shell\out\<имя>.out` и удаляет задание. Claude пишет
задания через `device_commit_files`, читает ответы через `device_stage_files`.

```
Claude outputs\
  claude-shell.cmd      запускать один раз, окно не закрывать
  shell\in\             сюда Claude кладёт задания
  shell\out\            отсюда Claude забирает вывод
  shell\alive.txt       метка времени, обновляется каждый цикл
```

`alive.txt` — способ проверить, что мост жив, не спрашивая пользователя: если его
время отстаёт больше чем на несколько секунд, окно закрыто.

**Про безопасность — сказать честно, а не умолчать.** Пока окно открыто, всё, что
попадёт в `shell\in\`, будет выполнено на машине без отдельного подтверждения. Файлы
заданий остаются видимыми до момента выполнения, вывод сохраняется целиком, закрытие
окна останавливает мост немедленно. Запускать его стоит на время работы, а не держать
постоянно.

**Сторожевой таймер (v2, 23.09.2026).** Первая версия запускала задание напрямую, и
первая же реальная команда — `git push` — повисла на запросе учётных данных и
заблокировала очередь намертво: `alive.txt` перестал обновляться, задание осталось в
`in\`, окно пришлось закрывать руками. Теперь каждое задание запускает
`shell\run-one.ps1`: оно ждёт 300 секунд, а потом убивает процесс вместе с потомками
(`taskkill /T /F` — git плодит вспомогательные процессы, которые переживают его самого)
и дописывает в `.out` строку `---TIMEOUT---`. Очередь после этого едет дальше.

**`git push` через мост не гонять.** Даже с `GIT_TERMINAL_PROMPT=0` он уходит в
менеджер учётных данных и ждёт человека. Пуш делается в GitHub Desktop, а мост — для
всего остального, включая `git add` и `git commit`.

**Задания не должны делать `cd`.** Родительский скрипт уже стоит в корне проекта, а
`%~dp0` внутри вызванного файла указывает на `shell\in\` — относительный переход из
задания уводит на два уровня не туда. Первый же реальный запуск на этом и споткнулся:
`fatal: pathspec '.env.example' did not match any files`.

**Остальные ограничения.** Вывод пишется в файл, интерактивные программы (те, что ждут
ввода) работать не будут. Кодировка вывода — UTF-8 (`chcp 65001` в начале скрипта), поэтому
русский текст в `.out` читается без искажений — в отличие от прежних логов, где
`xcopy` отдавал cp866 и в чат приезжала каша.

## Контрпики: один расчёт на весь сайт (с 25.09.2026)

Все цифры контрпиков считает `tools/build-hero-counters.js` из `data/our-matrix.json`
и `data/our-meta.json` → `data/hero-counters.json`. Метод log5: ожидаемая доля побед
пары по общим винрейтам обоих героев, `d = w − e` в п.п.; пары < 300 матчей не берутся.
Поля пары: `id, g, w, e, d`.

Кто читает `data/hero-counters.json` (поменял формат — проверь всех):
- `build-hero-pages.js` — «Кто контрит / Кого контрит» на `/hero/<slug>/` (по 4);
- `build-hero-guides.js` — таблицы на `/hero/<slug>/guide/` (по 8, колонка «К ожидаемому»);
- `build-guide-pages.js` — таблица в `/guide/counter-picks/` (dataTable `counters`, по 3);
- `js/app.js` — блок быстрой подготовки (`renderCountersInto`, по 8).

НЕ читает: `js/draft-tool.js` — у драфта своя модель прогноза (сглаженное отклонение
от 50 % по `our-matrix.json`, откалиброванное `tools/build-draft-calibration.js`).
Переводить его на log5 — только вместе с перекалибровкой и `tools/check-draft-math.js`.

Порядок в `tools/daily-update.js` и `tools/update-site.js`: build-our-stats →
build-draft-calibration → build-hero-counters → build-hero-pages → build-hero-guides →
build-guide-pages → sync-deploy → wrangler. Сбой контрпиков выкладку не останавливает
(на сайте остаются прежние). `deploy/hero/` и `deploy/guide/` пересобираются
автоматически, поэтому проверка «чужих правок в deploy/» их пропускает
(`GENERATED_DEPLOY` в daily-update.js). Руками эти папки не править — только исходники.
